# ObserverLauncher v3.0.0 - Plan (WORKING DOC)

> Status: SCOPED (2026-09-28). **3.0.0 = Headless core + CLI + MCP over headless + Templates.**
> Docker (3.1.0), CI/CD (3.2.0) and Remote (3.3.0) are DEFERRED - see "Deferred to 3.x" at the
> bottom. 3.0.0 is the breakthrough: the SAME backend + the SAME 70 MCP tools run with no window,
> on a VPS, so an AI can drive a headless server end to end. Tick an item only when written AND verified.

## Why this split

The original v3.0.0 draft bundled 8 phases. That is 3-4 releases of work in one version - hard to
ship, test and roll back. The core (headless + CLI + MCP + templates) is ~60% of the value at ~35%
of the risk, and is self-contained. Docker/CI/Remote stack ON TOP of it, so they must come after the
core is proven. A 3.0.0 that is only the core is still a genuine breakthrough; a 3.0.0 that tries to
be everything risks shipping none of it.

## Diagnosis (code-probed 2026-09-28, not guessed)

### What is ALREADY headless-friendly (good news, verified)
- `ctx` (`context.js`) is a plain object; it never touches `BrowserWindow`.
- `sendRaw()` already guards `if (ctx.win && !ctx.win.isDestroyed())` -> a push with no window is a
  no-op, not a throw. So the push layer needs NO change for headless.
- Feature modules take `(ipcWrap, ctx)`. The app's real "API" is just the set of
  `ipcMain.handle(channel, fn)` calls -> a fake `ipcMain` shim is enough to expose them
  headlessly (no event-bus rewrite).
- MCP `callTool` -> `tool.handler(ctx, args)`; per CONTRIBUTING these handlers reuse the same
  backend functions the IPC layer uses. => the 70 MCP tools are ALREADY 70 headless commands.

### What actually blocks headless (the real coupling - code-probed 2026-09-28)
TWO layers, not one:

**(1) Top-level `require('electron')` destructuring** - the harder blocker. In a plain Node process
(no Electron app object) `require('electron').app` is `undefined`, so `const { app } = require('electron')`
throws AT REQUIRE TIME. Files with top-level electron require:
- `settings.js:4` (`{ app }`) - required by context.seedInstances, mcp/server, almost everything.
- `runtime-state.js:13` (`{ app }`) - reached lazily from context.setServerStatus on EVERY status change.
- `textures.js:18` (`{ app, net, BrowserWindow }`) - net/BrowserWindow only on the icon-fetch path.
- `tunnel.js:132` (`{ app }` for playit dir) + `:327` (`{ shell }` for open-URL).
- `modpacks.js:6` (`{ app, dialog }`), `settings-handlers.js:5` (`{ app, dialog }`),
  `content-handlers.js:4` (`{ dialog, shell }`), `app-lifecycle.js:3` (window/updater - GUI only).
- `mcp/server.js` (`app.getPath` + `app.getVersion`), `mcp/tools.js:750` (`app.getPath` inline).
- SAFE already: `settings.js getSafeStorage()` uses lazy `require('electron')` inside try/catch -> null.

**(2) `app.getPath('userData')` call-sites** (settings.json + v3 backup, runtime.json, textures
cacheRoot, playit install dir, mcp-bridge.json, mcp-audit.log, launcher extract, JRE dirs, orphan tmp).

FIX = `src/main/data-dir.js`: `dataDir()` = `OBSERVER_DATA_DIR` env || lazy electron userData || a
per-platform default. THEN in each file: drop the top-level electron destructure and route the path
through `dataDir()`. Genuine GUI uses (dialog/shell/BrowserWindow/net) stay, but must move to
GUI-only code paths so a headless require never touches them.

### Headless-blocking GUI-only paths (code-probed)
- `confirmOnGui()` (mcp/server.js): if `ctx.onMcpConfirm` is not a function it takes the `else`
  branch and resolves FALSE immediately (no 60s hang - corrected). Headless never calls
  `registerMcpConfirm`, so `ctx.onMcpConfirm` stays undefined -> write/destroy auto-deny cleanly.
  BUT server.js also has a 60s timer for the GUI path; headless still needs an explicit policy so
  behaviour is deliberate, not accidental (Phase B / B4).
- `registerMcpConfirm` (confirm.js) is pure GUI: `ipcMain.on` + `ctx.send('mcp:confirm-request')`.
- `main.js` entry is Electron-only: `app.whenReady`, `protocol.registerSchemesAsPrivileged`,
  single-instance lock, `createWindow`, `setupAutoUpdater`.
- MCP HTTP server (server.js) serves ONLY `/tools`, `/resource`, `/rpc` - ALL token-gated. A Docker
  healthcheck cannot read the per-launch token, so a separate unauthenticated `/health` is REQUIRED
  (Phase C).

### Process model (code-probed)
`spawnServerProcess` (server-lifecycle.js:34-48) spawns `bash run.sh` / `cmd run.bat` / `java -jar`
as a CHILD of the launcher, and `recordSpawnedProcess` persists `{pid, processStartedAt}` to
runtime.json. So the launcher is ALREADY the parent of the JVM. NOTE: process events (exit/error)
fire OUTSIDE the IPC handler's ALS context and the code re-enters it explicitly
(server-lifecycle.js:335) - headless must preserve that re-entry or per-instance state will leak.

## Deferred to 3.x (outline only - spec each when its version starts)

### 3.1.0 - Docker integration
- process model already decided: launcher = PID 1, JVM = child (it already spawns the JVM).
- `observer docker create --type fabric --mods "sodium,lithium" --ram 4G` -> Dockerfile + compose.
- baked JDK (bypass java.js auto-install in-container); volume = server folder, OBSERVER_DATA_DIR unmounted.
- healthcheck uses `/health` (Phase C2). container-aware process kill (3rd platform context).
- docs/docker.md.

### 3.2.0 - CI/CD for modpacks
- GitHub Action: modpack.json -> OBL static verify (compat/deps/versions, pure fns) -> build ->
  boot smoke test -> publish.
- boot smoke test GATED (label `e2e`/nightly), not every PR (Minecraft needs 2-4GB + ~60s).
- auto-rollback needs PERSISTENT stability state (crash within N min of start = rollback), written
  to disk (today restartAttempts/manualStop are in-memory only).

### 3.3.0 - Remote management (gate hard, security design first)
- DESIGN GATE: do NOT expose MCP to the internet. Keep MCP loopback-only forever.
- thin remote control API: stable long-lived token + TLS + per-IP scope + READ-ONLY-ish subset
  (status/console/restart/players). NEVER expose DESTROY/install over tunnel.
- reuse existing RCON (rcon.js) for live control; MCP stays internal.
- prefer Tailscale (real identity, no port) over Playit; document both.

## Risks & open questions
- 3.0.0 = new entry point + shim + data-dir. NOT a rewrite. (Earlier "ctx is welded to Electron"
  was overstated; ctx is already window-free.)
- Linux unverified is a foundation risk for headless - hence Phase A first.
- `require('electron')` top-level may hide in more places than the ~10 found; expect to discover
  others on the first real headless run.
- Remote (3.3.0) is the single biggest security risk: bearer-token-only MCP over a public tunnel =
  full 70-tool access incl. DESTROY. Mitigate by NOT exposing MCP.
