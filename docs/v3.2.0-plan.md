# ObserverLauncher v3.2.0 - Plan (WORKING DOC)

> Status: IN PROGRESS (2026-09-29). **3.2.0 = CI/CD for modpacks.** The 3.0.0 core
> (headless + CLI + MCP-over-headless + templates) and 3.1.0 (Docker) are DONE. This version makes a
> modpack a DECLARATIVE, verifiable artifact: a version-controlled `modpack.json` that CI checks on
> every PR BEFORE anything is downloaded, then (gated) builds, boot-smokes and publishes.
>
> Tick an item only when it is written AND verified. Reference: `docs/v3.0.0-plan.md` (core),
> `docs/modpack.md` (manifest format), `.agent/memory.md` (gotchas).

## Why this version

- The MCP planner (`modpack-plan.js`) can already resolve/filter/de-duplicate a batch, but there is no
  WAY to describe a modpack declaratively and no gate that stops a bad pack before a 2-4 GB download.
- The v2.3.0 crash chain (wrong loader/MC) and the "same file written twice" class of bugs are cheap to
  catch STATICALLY. Put that in CI so it can never regress silently.
- The expensive part (a real Minecraft boot) belongs in a GATED job, not every PR (needs ~2-4 GB RAM,
  ~60s).

## Dependency / critical path

```
3.1.0 Docker ──> 3.2.0 CI/CD for modpacks ──> 3.3.0 Remote (gated, security-first)
                       |
      Slice 1 (static verify, pure) ──> Slice 2 (resolver + build) ──> Slice 3 (gated boot smoke + publish)
```

## Risks & open questions
- Network resolution in CI is flaky/slow; keep the pure verify as the DEFAULT gate and resolve only when
  a manifest is present. Cache if possible.
- CurseForge needs an API key (not bundled) - a manifest item from curseforge may not resolve in CI;
  surface a clear "needs key" error rather than a false reject.
- Boot smoke must NOT run on every PR (cost) - gate on label/nightly like `linux-boot`.
- Auto-rollback needs a persistent stability file; do not fake it with the in-memory counters.

## Verified facts (do not re-learn)
- `modpack-plan.js` + `server-compat.js` already hold the pure decision logic; REUSE, do not re-implement.
- `versionMatchesServer` only rejects when BOTH item metadata and the server are known (no false rejects).
- CLI local commands (templates/init/docker/set-folder/modpack) run BEFORE the `COMMANDS` lookup and need
  NO backend boot.
- MCP tool registry = `src/mcp/tools.js`; `bridge.js STATIC_TOOLS` is a hand-copied drift-guard twin.
  The 3.2.0 verify is CLI-only (no new MCP tool) so there is nothing to mirror - keep it that way unless
  a tool is explicitly needed.
