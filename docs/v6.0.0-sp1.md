# SP1: Pinggy tunnel interface (v6.0.0 spike)

> Status: SP1 DONE 2026-10-17. TCP and UDP tunnels both measured end to end. Anonymous free tier
> WORKS with any password piped to stdin. Public address format: `<proto>://<id>.run.pinggy-free.link:<port>`.
> Free tier expires after 60 minutes. NO token, NO account, NO API key needed.
> Gate for Track A2. No product code until this file records the exact command shape and output.

## Question

Can a free Pinggy tunnel carry a local **TCP** socket and a local **UDP** socket, and what exactly
must the app parse (public address line, reconnect signal, time limit)?

## Local facts (measured, no network)

Probe script: `.agent/spikes/sp1-pinggy-probe.js`.

- Pinggy CLI binary: NOT FOUND on PATH or in the usual install folders.
- OpenSSH client: present at `C:\Windows\System32\OpenSSH\ssh.exe`.
- Loopback TCP listener + connect: works (ephemeral port bound and reached).
- Loopback UDP socket send/receive: works (ephemeral port bound and reached).

Conclusion so far: a Windows install has a usable SSH client out of the box, so the free tier can be
driven with `ssh` alone and needs NO bundled dependency. The Pinggy CLI is optional, not required.

## Reachability (measured)

`a.pinggy.io:443` opens a TCP connection from this machine (YES). So the outbound path exists and
an `ssh -p 443` tunnel can reach Pinggy. No account was used for this check.

`ssh` cannot be launched through the agent's shell tools (blocked by design: a remote shell is not
something the sandbox allows). That is an environment limit, not a project bug. The network step
below stays manual.

## MEASURED (TCP, 2026-10-17, user-run) - this is the reference output

Command:
```
echo test| ssh -p 443 -T -R0:localhost:25599 tcp@free.pinggy.io
```

Output (verbatim):
```
tcp@free.pinggy.io's password:
Allocated port 3 for remote forward to localhost:25599
You are not authenticated.
Your tunnel will expire in 60 minutes. Upgrade to Pinggy Pro to get unrestricted tunnels. https://dashboard.pinggy.io
tcp://tsdcx-103-216-221-97.run.pinggy-free.link:39069
```

### What this tells us (final, no guessing)

1. **Password is ANY string.** `echo test|` worked. Pinggy does not check it in anonymous mode.
   An empty line would also work. So the adapter sends one dummy line to stdin, not a real secret.
   This ALSO explains the earlier hang: cmd.exe could not type into the password prompt, but piping
   bypasses that completely. Product code must pipe, never rely on the user typing a password.
2. **No token, no account, no API key** for the free tier. Simpler than the earlier hypothesis.
3. **Public address format:** `tcp://<id>.run.pinggy-free.link:<port>`. The id looks like
   `<hex>-<ipv4-with-dashes>` (a per-tunnel random name). The port is the PUBLIC port (39069 here),
   NOT the `Allocated port 3` line (that is Pinggy's internal SSH forward).
4. **Free-tier limit:** exactly 60 minutes, printed as a plain sentence. The tunnel is cut at the
   end. The adapter should log it and offer to restart at ~55 minutes.
5. **Process runs in the FOREGROUND** and stays alive until the limit or Ctrl+C.
6. The `tcp://` scheme is the shareable address for a raw TCP tunnel. For a Bedrock UDP tunnel use
   `udp@free.pinggy.io` and expect a `udp://<id>.run.pinggy-free.link:<port>` line.

### What a real (non-anonymous) tunnel needed earlier

With `a.pinggy.io` (the Pro host) an anonymous `PreferredAuthentications=none` was refused with
`Permission denied (publickey,password)`. The FREE host is `free.pinggy.io`. Do not use `a.pinggy.io`
for the free tier.

## (superseded) First SSH attempt against the Pro host

```
ssh -p 443 -o StrictHostKeyChecking=accept-new -T -R0:localhost:25599 tcp@a.pinggy.io
Warning: Permanently added '[a.pinggy.io]:443' (RSA) to the list of known hosts.
tcp@a.pinggy.io's password:
```

Same for `udp@a.pinggy.io`. So:

- Host-key trust works: `accept-new` added the key once, no prompt.
- Pinggy demands a PASSWORD. The free tier is NOT anonymous. A bare spawn with `BatchMode=yes`
  would exit at this prompt, not hang (good), but it would also never open a tunnel.

Consequence for A2: the adapter cannot just spawn `ssh ... tcp@a.pinggy.io`. It needs credentials.
Two standard Pinggy auth paths exist (to confirm against their docs before coding):

1. **Token in the user name**: `<token>+tcp@a.pinggy.io` / `<token>+udp@a.pinggy.io`. The token
   comes from the Pinggy dashboard. Simplest for a GUI app: one secret field, spawn ssh with the
   token prepended to the user, no key management.
2. **SSH key**: the user uploads a public key to the Pinggy dashboard once, then `ssh -i <key>`
   works without a password. More setup for the user, but no token stored in the app.

Recommended for A2: path 1 (token). It matches the app's existing secret pattern (like
`curseforgeApiKey`, `remoteToken`) and needs no key file. A2.4 gains a per-install `pinggyToken`
secret; A2.6 `pinggyPath` still points at `ssh.exe` (not the Pinggy CLI).

BLOCKED: the network step still needs a real tunnel to read the public address line format. That
needs a Pinggy account + token. Ask the user before assuming the address format.

## SSH flags the adapter MUST pass (known before the tunnel run)

A bare `ssh ... tcp@a.pinggy.io` will misbehave when spawned with no TTY. These are required no
matter what the Pinggy banner says:

- `-o StrictHostKeyChecking=accept-new` - the first run would otherwise sit on an interactive
  `yes/no` prompt and hang the spawn. `accept-new` trusts a new host once, still refuses a changed key.
- `-o BatchMode=yes` - never prompt for a password / passphrase; fail instead of hanging.
- `-o ServerAliveInterval=30 -o ServerAliveCountMax=3` - keep the link alive and detect a dead one
  within ~90s (a silent NAT drop otherwise looks like a healthy tunnel).
- `-o ExitOnForwardFailure=yes` - exit immediately if the remote forward is refused. Without it ssh
  keeps running with NO tunnel, and the A2.3 fallback would never trigger.
- `-T` - no pseudo-terminal (we only parse stdout).
- `-R0:localhost:<port>` - ask Pinggy to allocate the remote port (the `0`).

These are the A2.2 argv defaults. The network step confirms the address line format and the
free-tier limit message, not these flags.

## UDP MEASURED (2026-10-17, user-run)

Command:
```
echo test| ssh -p 443 -T -R0:localhost:25599 udp@free.pinggy.io
```
Output (verbatim, address line):
```
udp://toqpo-103-216-221-97.run.pinggy-free.link:41140
```

Same banner (Allocated port / not authenticated / 60 minutes). Only the scheme (`udp` vs `tcp`)
and the random name differ. So ONE parser handles both: the line matches
`^(tcp|udp)://([\w.-]+):(\d+)$`.

## Decisions this unlocks (FINAL)

- **A2.2 argv builder**: `ssh -p 443 -o StrictHostKeyChecking=accept-new -o BatchMode=yes
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes -T
  -R0:localhost:<port> <proto>@free.pinggy.io` where proto is `tcp` or `udp`. The adapter pipes
  one dummy line (`test\n`) to stdin immediately, then closes stdin. NEVER rely on the user typing
  the password (the cmd.exe hang was a terminal bug, not a Pinggy one).
- **A2.2 address parser**: `^(tcp|udp)://([\w.-]+):(\d+)$` on any stdout/stderr line. The captured
  host is the shareable address; the captured port is the PUBLIC port. The `Allocated port N` line
  is Pinggy's INTERNAL SSH forward and must be ignored.
- **A2.2 timeout**: if no address line within ~25s, kill the child and report a start failure.
  The 60-minute expiry is a plain sentence; the adapter should surface it and offer a restart at
  ~55 minutes. Do not parse the expiry text; use a fixed 55-minute timer.
- **A2.3 fallback**: the trigger is "Playit start failed OR reported over its agent limit". Because
  Pinggy free is anonymous, the fallback needs no credential step, only the local `ssh`. If `ssh`
  is missing, A2.3 reports 'ssh not available' instead of trying (a clean failure, not a hang).
- **A2.4 setting**: NO per-instance Pinggy token. The one setting is per-install `pinggyPath`
  (usually the system `ssh.exe`), used only if it is not on PATH. NO secret field.
- **A2.6 `pinggyPath`**: points at an SSH client, not the Pinggy CLI. `findSshBinary()` mirrors
  `findPlayitBinary()`: settings override, then known Windows OpenSSH path, then PATH.
- **Address protocol**: the shareable address is the `<proto>://...` line itself. The app stores it
  in the existing per-instance `tunnelAddress` (no new field). For Bedrock crossplay the user shares
  the `udp://...` line; for Java the `tcp://...` line.
