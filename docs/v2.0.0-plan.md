## Why 2.0.0 is a major version

1.5.0 is a **single-server manager**: settings (RAM, Java path, JVM args) are
stored globally in one `ctx`, and the folder picker *replaces* the active
server (losing live state: metrics, console, players). That is the single
biggest architectural limit. The version bump is justified by moving to
**multi-instance**, not by a pile of small features.

## HEADLINE: Multi-instance management

Turn ObserverLauncher from "one server at a time" into "manage N servers".

### Target behaviour
- A persistent sidebar lists every instance (add / rename / remove).
- Each instance owns its settings: RAM, JVM args, Java path, tunnel config,
  schedule, backups, server folder.
- Metrics / console / players / backups / tunnel / schedule are **scoped to the
  active instance**.
- Starting instance B while A runs is allowed, with a RAM warning.
- The old folder picker becomes "Add instance" - additive, not replacing.

### Phased implementation (A -> B -> C)

**Phase A - foundation (no UI change yet)**
1. Refactor `ctx` to `instances: Map<id, InstanceState>` + `activeInstanceId`.
   Access state through `ctx.active()` instead of direct fields.
2. Per-instance settings; migrate the current global settings into the first
   instance (new migration version, same pattern as v2->v3 backupRetention).
   MANDATORY: back up settings.json BEFORE migrating (a failed migration must not
   lose the user's config).
3. Tests: run two instances; assert no cross-leak of metrics/console/players.
4. RCON transport (DECIDED, from PocketMC): replace stdin console commands with a
   managed RCON client. stdin is per-process and can deadlock on high load; RCON
   is the MC standard, lifecycle-independent, and routes by PORT not process
   handle (simplifies multi-instance routing). Per-instance: rconPort = random,
   password = random, bind 127.0.0.1 ONLY; app enables rcon in server.properties
   on instance create. Fallback: stdin for the first ~10s until RCON is ready.
5. JRE ISOLATION per instance (DECIDED, from PocketMC). `javaPath` moves from
   global settings to InstanceState. JREs cached by major version under
   userData/runtimes/jre-<major>/ (shared download), instance references it.
   This lets server A (Java 17) and B (Java 21) run simultaneously - the real
   difference between "multi-folder" and "multi-instance".
6. ORPHAN CLEANUP (DECIDED, 3-tier - favour convenience): (t1) PID alive +
   stored state stopped AND process name matches java -> auto-kill, log it
   (no prompt). (t2) PID alive + stored state running/starting -> show ONE
   dialog: [Reconnect] (default, safer: re-attach, tail log, try RCON) /
   [Stop it] (graceful shutdown). (t3) PID alive but NOT java (PID reuse) ->
   never kill, clear PID, log warning. Store process START TIME alongside PID
   (unique) to detect reuse (win: wmic creationdate; linux: /proc/N/stat).
   PREREQ (VERIFIED + DONE 2026-09-22): kill logic is NOT in platform/*.js -
   platform exports no kill fn; the tree-kill is kill.js killTree(). Windows is
   OK (taskkill /T /F). Linux is PARTIAL: killTree = SIGTERM to the DIRECT child
   only; the real tree is covered only by the in-memory forceStopServer block
   (server-lifecycle.js:231-245). Orphan cleanup cannot reuse that (serverProcess
   is lost on crash) -> it MUST resolve findJavaDescendant(storedPid) itself.
   [x] DONE: platform.getProcessInfo(pid) added (win+linux) = the pid-alive /
   start-time helper; orphan tier-3 reuses it for PID-reuse detection.
7. PORT LEASE per instance: each instance owns serverPort + rconPort; ensure no
   conflict within the app and warn on a port already taken by another process.
8. CROSS-INSTANCE PATH SAFETY: safeTarget must take the INSTANCE root (not the
   global root). Add a test: importing into instance A with a path that resolves
   into instance B must be rejected.

**Phase B - UI**
9. Persistent instance list in the RAIL (DECIDED): a new tier above/beside the
   existing 3 nav groups. Each item = status dot (stopped/starting/running/
   stopping) + click to switch active + quick start/stop; full control stays in
   the instance's tab. Background instances show a running badge (console only
   for the active one). The old folder picker becomes "Add instance" (additive).
10. Scope every live/stateful view to the active instance.
11. Allow concurrent starts + RAM warning.

**Phase C - hardening riding along (cheap, do together)**
12. P0: verify downloaded binaries (Playit agent: pinned SHA-256 per platform +
   Authenticode signature check - PocketMC does both).
13. P0: regex timeout helper (Date.now() guard) for log/regex paths.
14. P1: architecture tests (see below).
15. P1: atomic-write architecture test.
16. Graceful shutdown, detailed (from PocketMC): send `stop` -> poll exit every
   500ms up to 15s -> SIGTERM/taskkill -> wait 5s -> force kill (-9//F). LOG
   which instance was force-killed (world may not be fully saved). Critical when
   stopping one of N instances.
17. PII scrub (from PocketMC): scrub IPv4/email from console/logs before they go
   to MCP/AI or export. Hook into doctor.analyzeConsoleLines.

## Multi-instance deep notes (decided / to design)
- TUNNEL (Playit) is the hardest open problem. Playit is a system daemon whose
  tunnel config lives on the playit.gg dashboard; the app cannot discover
  addresses. With 1 instance a manual paste box is fine; with N instances the
  user must create N tunnels. DECISION DIRECTION: tunnel config becomes
  per-instance, but the DAEMON lifecycle is GLOBAL (one playit daemon, N tunnel
  configs). Needs a TunnelManager tracking which instances use the daemon so
  stopping B never kills a daemon A still needs (replaces the single
  ctx.tunnelStartedByApp flag). settings.autoTunnel becomes per-instance.
  Treat as its own sub-phase, not inside the core ctx refactor.
- RAM BUDGETING: before starting instance N, sum memoryMax of all running
  instances + the new one; compare to total system RAM (read once at boot via a
  new platform.getTotalMemory()). Warn >80%, confirm/block >100%.
- METRICS ROUTING: per-instance ring buffer (ctx.instances.get(id).metrics
  History). Background instances keep sampling so no data is lost on switch; the
  UI shows the active instance. Extend the existing non-overlap `sampling` guard
  to N instances.
- fs.watch SCOPING: only watch the ACTIVE instance; pause/relax watchers for
  background instances (Linux inotify default 8192 watches/user is a real
  ceiling with many large instances). Re-attach on switch.
- BACKUP RETENTION is per-instance: pruneBackups must operate on the instance
  root. The world-backup-auto- prefix stays usable.

## Lessons from PocketMC (PocketMC/pocket-mc-windows)
- PocketMC is a .NET 8/WPF Windows app managing Java + Bedrock + PocketMine
  servers, multi-instance native, MIT. It has ALREADY shipped the multi-instance
  step we are planning -> strong external validation that multi-instance is the
  right 2.0 headline, not feature creep.
- ADOPT (already folded into the phases above): (a) RCON transport instead of
  stdin (PocketMC: "Standard I/O is deprecated in favor of a robust managed RCON
  client, eliminating synchronization deadlocks"); (b) graceful shutdown loop
  (15s) so worlds save before exit; (c) PII scrubbing of IPv4/email before
  AI/export; (d) DataProtector/safeStorage for credentials; (e) SHA256 + hash
  verification on ALL downloads incl. Playit; (f) single source of truth config
  (their pocketmc.yml) - never hardcode versions.
- DO NOT COPY: cloud backup (OAuth + proxy backend), remote control (WebSocket
  console + tunnel providers), AI session summaries, Bedrock/BDS/PocketMine
  support, telemetry, and the 6-layer Clean Architecture / DI / MVVM stack.
  PocketMC is a multi-person, multi-month codebase; importing its surface area
  contradicts ObserverLauncher's no-bundler, plain-Electron, single-maintainer
  design. Pick one big thing (multi-instance), ship it, then the next.

## Deep dive: ctx access model (KEY DESIGN)
- VERIFIED: every MCP tool handler is called through ONE choke point -
  server.js callTool(ctx, name, args, cfg) does `await tool.handler(ctx, args)`.
  Same for the ~57 IPC handlers: they close over the shared ctx object.
- PROBLEM: per-instance fields (currentServerPath, serverProcess, ...) are read as
  direct property access on ctx. Swapping ctx.activeInstanceId around a handler
  RACES across awaits (two concurrent calls).
- SOLUTION: AsyncLocalStorage (Node built-in, zero deps). ctx.inst() returns
  als.getStore() ?? ctx.activeInstanceId; callTool runs the handler inside
  als.run(instanceId, ...). Carries the current instance across awaits WITHOUT
  mutating global state -> no race, and tools.js / most handlers need NO change.
  ctx.active() stays the single accessor; per-instance fields become accessors
  that read through it. This is the missing piece for the whole ctx refactor,
  not just MCP.

## Deep dive: tunnel multi-instance UX
- KEY INSIGHT: the Playit DAEMON manages N tunnels from its cloud config - the
  app does NOT route per-instance. So TunnelManager only tracks WHO wants the
  daemon, not the tunnels themselves:
    daemonUsers: Set<instanceId>; daemonOwnedByApp: bool.
  instance start + autoTunnel -> add to daemonUsers -> playit start if not
  running (ownedByApp=true). instance stop -> remove -> playit stop ONLY when
  daemonUsers is empty AND ownedByApp (never kill a user-run daemon).
- tunnelAddress stays per-instance (manual paste, as today). refreshTunnel runs
  ONE `playit status` (daemon is one) and updates the pill for every instance
  using it - not N calls.
- HARD LIMIT (not a bug): each instance needs its own tunnel created on the
  playit.gg dashboard -> a new multi-instance user sets up N of them manually.
  Add a small checklist (which instances have an address). Do NOT force every
  instance to have a tunnel: common case = one public server, others LAN-only.
  autoTunnel stays default false per-instance.

## Deep dive: downgrade path (one-way door)
- VERIFIED: migrate() is forward-only. A settings.json at version 4 read by 1.5.0
  (3 migrations) skips the loop but keeps all fields (out = {...settings}); 1.5.0
  ignores instances[] and no longer finds a root serverPath -> the user appears
  to have lost every per-instance setting (RAM, java, tunnel). No crash, but
  looks like data loss. So v4 IS effectively one-way.
- DECISION: accept one-way + make it safe: (a) migration writes settings.v3.bak
  .json; (b) ADD a version-gate in loadSettings: if settings.version >
  latestVersion, keep values but warn "settings from a newer version, some
  settings will be ignored" instead of silently dropping. Do NOT try to keep a
  root serverPath mirror (drift). Document the downgrade step in release notes.

## Deep dive: instance identity, rename, delete policy
- id = short random hex (crypto.randomBytes(4).toString('hex')), stable across
  rename; the migrated first instance keeps the fixed id 'default' (recognisable
  in backup/rollback). name = display only, default basename(serverPath) or
  'Server 1', renameable without changing id.
- DELETE = remove from the list ONLY, never touch the folder (the app must never
  delete Minecraft data). destroy-tier confirm; refuse while the instance is
  running (stop first). Deleting the last instance -> instances:[],
  activeInstanceId:null -> reuse the existing .has-server first-run UI.
- BLOCK two instances pointing at the SAME serverPath (two processes on one
  folder corrupt worlds) - reject on add with a clear message.

## Deep dive: IPC event volume with N instances
- VERIFIED per-instance, continuous pushes: server:metrics (~1/s, 8 sites in
  server-metrics.js), server:live, server:log (appendLog), server:files. With N
  BACKGROUND instances these would be N x IPC traffic + N x renderer redraws for
  a view nobody is looking at.
- DECISION: gate per-instance channels in the MAIN process - sendForInstance
  (instanceId, channel, data) returns early unless instanceId ===
  ctx.activeInstanceId. Background instances KEEP sampling (metrics tick + ring
  buffer) - only the IPC is skipped. On switch the renderer calls
  getInstanceSnapshot(id) once (console tail + metrics history + files + status)
  to repaint immediately.
- NOT gated: server:state (the rail status dot must reflect a background
  instance's crash/stop). server:log is gated EXCEPT error lines (type 'error' or
  text matching ERROR/Exception) which still go through with an instanceId so the
  rail can show a red badge. Global channels (app:update-*, mcp:*, tunnel:*) are
  unaffected.
- CODE IMPACT: appendLog and every per-instance ctx.send must route through
  sendForInstance instead of ctx.send (mechanical, same class as the ctx
  refactor). Big win at N>=2: background metrics cost 0 IPC instead of N/s.
